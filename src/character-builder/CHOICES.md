# Character Builder choices

Use the full list with collapsible rows by default for new Android catalog choices. Feat is the reference implementation. Class and Equipment use sectioned lists. Ancestry, Theme, class feature choices and power choices use split readers as listed below.

Keep tab fields and sheet rows consistent. Use the compact `Field` for saved or empty choices on a tab. The tab label already names the page. In the sheet, reuse `ChoicePickerSheet`, `CollapsibleChoiceList`, compact `ChoiceCard` rows, and `ChoicePickerActions`. These components set the sheet height, gutter, row spacing, folio scrollbar, and footer. Put option details inside the expanded row at compact size. Use `PlainChoiceDescription` for plain text and `ControlledDescription` for authored HTML.

## Picker layouts

| Choice | Default layout |
| --- | --- |
| Feat and other catalog choices | **Full list with collapsible rows (default).** Use the Feat picker in `CatalogChoiceList` as the reference. A new pick expands its card and replaces the draft. Tapping the selected row toggles its detail. |
| Class | **Sectioned list with collapsible rows.** Reuse `ClassPicker` in new character creation and Progression. It groups classes by role, sorts names within each group, and shows fixed-width power-source badges. Ineligible classes always appear in red in their role group. `SectionedChoiceList` accepts ordered sections and caller-supplied rows. |
| Equipment | **Sectioned list with collapsible rows.** Use the Class picker’s `SectionedChoiceList`. Group weapons by authored proficiency tier and armor by Light or Heavy. Show ineligible items in red within their own section and let players inspect them. |
| Power-only catalog, including attack, utility, and power replacement | **Split reader.** Reuse `PowerChoiceReader` and `CatalogReaderPanes`. Put compact rows above an independently scrollable `PowerBlock`. Power search acts on the current pool and matches names and authored rules. Pick the earlier slot before staging a replacement. |
| Class-owned catalog choices with feature options | **Split reader.** Use the compact list and independently scrolling detail pane to show the option's full authored rules, granted features and power cards. |
| Ancestry or Theme | **Split reader.** Reuse `AdvancementChoiceReader` and the independently scrolling details pane for flavor, attributes, grants, powers, and choices or modifications where available. |
| Skill increase | **Skill by rank matrix** in the usual picker sheet, one milestone at a time (`SkillMatrixEditor`; cell behaviour in `SkillMatrix.kt`). One press on an affordable cell buys up to that rank, the ✓ undoes it and every other cell explains itself. The Levels card (`SkillIncreaseCard`) lists one chip per raised skill. Save stages `BuilderEdit.SkillIncreases` and is disabled while this milestone is illegal; a draft that would break a later milestone warns but can be saved. |
| Environment or Upbringing | **Disabled for the 2.0 playtest** by `ModernCreation.BACKGROUNDS_ENABLED`. When enabled: full list with collapsible rows, origin description and offered skills inline, saved through `backgroundEdit` so a stale skill clears with it. |
| Structured values, proficiencies, or ability edits | **Full sheet with direct controls.** Use compact rows for values and skills, and steppers for allocation. The free skill editor stages exactly three picks and counts those left in a fixed `PickTallyHeader` above its list, the same header as the skill matrix. Skill pickers (`SkillPickList`) show no instruction line. Class, free and theme skills have their own level 1 tiles (`startingSkillTiles`) instead of ordinary rows; picker rows and their blocking come from `skillPickRows`. |

The layouts share a fixed Progression sheet height of 710 dp capped at 91% of window height, with actions below the scrolling content. Swipe from the top handle, press Back, tap outside, or use Cancel to dismiss a picker. Scrolling inside the list or reader keeps the sheet open. Use the existing folio scrolling and choice card styles. In a split reader, an explicit row tap can stage a draft. The reading pane follows the inspected row, the visible selected row, or the first visible row in that order. Opening the sheet, searching, and inspecting ineligible entries only change what can be read. Reset detail scroll when the inspected entry changes. Start with [ProgressionScreen.kt](android/src/main/kotlin/dev/modern4e/builder/ui/screens/ProgressionScreen.kt) and [ChoiceCard.kt](android/src/main/kotlin/dev/modern4e/builder/ui/components/ChoiceCard.kt).

## Automatic grants and equipment

Ability Increase rows show a right-aligned value using the current known ability total, replacing this milestone's saved increase with the draft. Selecting or deselecting an ability previews its +1. Save requires two distinct picks. Clearing removes both from the preview. Keep other milestones and automatic increases included. Armor sorts by ascending authored AC bonus within its existing Light/Heavy sections, then A–Z, with unknown bonuses last.

Levels renders automatic features and powers from the engine at the level they are acquired. Standalone grant cards use the same compact label and value layout as choice fields and expand for reading. A feature authored with `grantDisplay: CHOICE_INTRODUCTION` supplies the picker introduction for its own choices. Use `GRANT_SUMMARY` for a feature whose text only restates grants already shown at that level. Use the default `STANDALONE` whenever the feature has rules of its own, including when it also has choices or grants. Keep editable substitutions in their existing choice rows. At level 0, pair Class with Theme. Pair Ancestry with Ancestry Language when offered and retain the engine’s acquisition level when saving the language. Show starting ancestry power choices full width immediately below the Ancestry row and keep their existing decision slots. After the level 0 choices, show starting grants in Ancestry, Class, and Theme sections. Include starting features and powers from all three sources.

Equipment uses the sectioned list for its six optional equipped slots. Its catalog is prepared from Home. Keep all items in their authored categories and use red styling for items the character lacks proficiency to select. Allow Improvised weapons regardless of proficiency. The Implement slot can select a standalone implement or refer to a weapon already equipped in another slot. Armor and Neck stage an enhancement from +0 to +6 alongside the selected item. Use the existing shared equipment edits so saving or clearing gear recalculates defenses. Equipped fields open their choice sheet directly, with details inside the picker.

## Choice identity and edits

1. **Find the slot.** For baseline choices (class, ancestry, theme, feats, paired ability increases, Skill Increases, paragon path, daily replacements), find the root slot by category with `AdvancementRules.rootSlot`; the engine offers the same slots as deferred root offers in `state.rules.choices` with `required`/`filled` state, and the missing-choice count reads those offers. Never hard-code root slot IDs or schedule levels; `Progression.level` only turns the shared schedule into display strings. For authored choices, use the engine's active inline `EngineChoice` and its acquisition level through `Progression.levelChoices`, which excludes root offers. The stable `ChoiceSlotId(sourceInstanceId, choiceId, ordinal)` identifies the occurrence being edited. Reuse the source occurrence ID so its nested choices keep their identity. Automatic grants can supply the displayed value. Authored grant replacements use the engine's offered choice.
2. **Read the offered values.** Entry choices go through `BuilderSession.progressionOptionRows`. Proficiency and structured value choices read the slot's offered skills or values from `state.rules.choices`. Keep choice labels, section placement, and required-choice indicators in the existing Progression helpers.
3. **Stage and save.** Initialize the sheet from the saved choice or displayed grant. Stage a `BuilderEdit` locally and pass it to `BuilderSession.edit` on Save. Cancel discards the draft, and Clear stages a removal where supported. Use `progressionEntryInstance` for early entry edits, typed edits for values/proficiencies/allocation, and `BuilderEdit.Batch` for changes that must succeed together. Through level 20, shared operations check acquisition-level choices, feats, paragon paths and power replacements. At levels 8, 14 and 28 paired ability increases use `BuilderEdit.Advancement`. The level 21 all-ability increase is automatic. Replacement candidates load only after selecting an active earlier class attack acquisition, and save through `BuilderEdit.ReplacePower`. A progression replacement stores both the prior target slot and the new choice.
4. **Verify the normal entry point.** Open the choice from Levels or its existing caller. Check the saved value on reopen, draft changes on tap, cancellation, and any relevant eligibility, loading, or replacement state. Find the unit suites under [Progressive feat listing and picker tests](../../tests/README.md#progressive-feat-listing).

Use [Progression.kt](android/src/main/kotlin/dev/modern4e/builder/Progression.kt) for slot discovery and labels, [BuilderSession.kt](android/src/main/kotlin/dev/modern4e/builder/BuilderSession.kt) for editing and option loading, and [ENGINE.md](shared/ENGINE.md) for persistence and rules contracts.

## Catalog loading and eligibility

- Power level badges prefer `mechanics.powerProfile.level`; grouped prerequisites are a legacy fallback. Omit class and level routing from power preview requirements because class pools and the badge already communicate them. Preserve other prerequisites and concise missing conditions. Previews show one Requires line: red with a cross when unmet, green with a check when met. Ancestry/class combination feats belong to the Ancestry tab, with ancestry scope followed by ordinary class eligibility checks.
- Feat pickers cap visible tiers at the edited slot's acquisition level: below 11 show Heroic only, 11–20 show Heroic/Paragon, 21+ permit Epic. Keep same-tier ineligible entries visible. Power reading panes show readable access/prerequisite requirements and concise unmet requirements from the evaluated slot; preserve grouped alternatives and acquisition-time eligibility rather than guessing from current character totals.
- In completed picker results, sort feats Epic, Paragon, Heroic and then case-insensitive A–Z; sort powers by descending authored level and then case-insensitive A–Z. Sort eligible and ineligible groups separately, with ineligible rows at the bottom. Categorized Class and Equipment lists retain their section ordering instead. Unknown power levels sort last. Preserve search filtering and selection identity when order changes.
- Load the requested slot and feat tab from catalog metadata before resolving definitions. The Feat picker opens on Class. Class and Ancestry tabs scope indexed entries to the character's applicable access IDs, including multiclass or Past Life qualifications where applicable. Index scope narrows the candidates. Eligibility still comes from the shared choice evaluator.
- Paragon Path rows use indexed `pathClassIds` to exclude unrelated classes before loading definitions or evaluating candidates. Include class and qualifying multiclass access acquired by the path slot's level. Multi-class access routes retain a path when any route matches; unscoped Zeitgeist and legacy rows continue through ordinary eligibility checks. Keep the shared filter in `ChoiceEvaluation` so the picker, direct option listing and cached reopen agree.
- Reuse `BuilderOptionListing` for batched checks and the Android `OptionListingCache` (owned by `BuilderSession` as `listings`) for cancellation, cache invalidation, and warm-up. The cache owns its character/content snapshot, the listing working set, warm priorities, yielding and the heavy-work lock; it never takes the session's edit lock, and `BuilderSession` holds no cache code. Warm-up uses active picker slots, queues unmade choices by level before choices already made, does only the work a retained listing still lacks (`BuilderOptionListing.isComplete`), yields to an open picker or pending edit between small batches, and shares its results with the open sheet. Update `OptionListingCache.warmTargets` when a change affects which choices Levels can open.
- On Android edits, rebase invalidated listings onto fresh character rules while sharing the unchanged catalog read session. Preserve definitions and preview grants, regenerate candidate metadata/scope, retain proven-independent feat/power row results, and mark affected rows unchecked with `UNRESOLVED` eligibility and empty diagnostics. Pending rows remain unselectable and cannot regain checked status merely through another rebase. Active/unknown dependencies and non-entry edits may require checking every row; they still retain content. Explicit catalog refresh or switching/reloading characters starts a fresh content snapshot. `ListingRetention.verdict` in shared decides whether a listing survives an edit (dropped, kept, or rebased with the rows to recheck), using `EffectProfile` for what an entry can supply and `ChoiceCacheDependencies` for per-row proofs; put new pool/occurrence/acquisition guards there, not in Android code. `BuilderOptionListing.retainedAfter` applies a verdict, and `OptionListingCache.committed` applies it to every retained listing after an edit.
- Android cache invalidation separates attack At-Will, Encounter and Daily pools from the Utility family. Passive power changes preserve completed independent lists; same-family siblings and later slots refresh for duplicate checks. Feats preserve power results when their mechanics cannot affect the candidates' authored requirements or power-pool rules. Skill-dependent powers still refresh for relevant proficiency grants. Explicit named/selected-power dependencies, active mechanics, unfinished/unresolved listings, structural edits and catalog changes retain conservative invalidation. The edited slot can keep its own checks when its occurrence and pool stay stable, including after clearing.
- Power pool lists offer only powers of the character's own classes (including multiclass feats) and powers any class can take. The engine can offer another class's powers when a saved power names that class as a prerequisite, so `ChoiceEvaluation` drops them, keeping only the power already saved in the slot so a leftover wrong-class choice stays visible and replaceable. Power replacement lists are not yet filtered this way.
- Feed the rows to `pickerOptions`. The sheet shows progress until the current list finishes checking. All checked rows are visible. Ordinary lists put eligible entries first and ineligible entries last, sorting each group by tier/level/name. Class and Equipment lists keep all entries in their normal categories. Style ineligible titles red; omit generic automation/validation warnings from picker rows and reading panes; power previews may name unmet authored prerequisites concisely. Keep authored descriptions and prerequisite text. There is no eligibility visibility toggle; detailed diagnostics belong to Validation. Stage an ineligible edit only in pickers that explicitly allow it. Equipment always shows ineligible options for inspection. Search, filters, loading, and unavailable definitions never stage an edit.
