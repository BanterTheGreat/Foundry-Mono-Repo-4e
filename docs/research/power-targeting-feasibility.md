# Power targeting panel and attack activation: feasibility

Research date: 25 October 2026. Scope: a design investigation, with no runtime changes. Target: Foundry v14 and DnD4e **0.9.3**, not current upstream.

## Conclusion

**The revised flow is feasible without a DnD4e fork.** Use Ability starts an independent activation session: show a square range preview, open a targeting panel, and post a provisional power card without consuming a use. The player selects targets and presses Attack to enter the normal attack dialog. The HUD only starts this service; selection does not automatically attack. The main compatibility work is deferred resource consumption, reusable card rendering, exact-count validation, and keeping validated targets stable through the native dialog.

Two new per-power Automation fields supply the missing enablement and exact target count. They do not encode ally/enemy restrictions, creature types, or special requirements, so advisory validation initially covers configured count, supported range, and basic target accessibility. Broader legality requires additional structured metadata. These are design conclusions from the verified source below, rather than claims that one existing API supplies the entire interaction.

## What the current code actually does

The HUD already has a narrow integration point: `HorizontalActorDisplay.onPower`. Right-click opens the power sheet; an NPC attacking power consumes a limited use and calls `power.rollAttack()`; other powers call `actor.usePower(power)`. HUD hotbar power slots route to the same handler. The explicit chat action separately calls `actor.usePower`. See [HUD controller](../../src/dnd4e-health-display/scripts/actor-display/actor-display.js), lines 365–414 and 632–638, and [power controls](../../src/dnd4e-health-display/scripts/actor-display/actor-display-horizontal.hbs), lines 41–68.

**PC power activation currently differs from NPC activation.** In the pinned system, `Actor4e.usePower` normally consumes a limited use and posts the power card. It does not normally open an attack dialog. Its `fastForward` path posts the card, places an area template when applicable, then rolls attack, damage, and healing with fast-forward enabled. Consequently, `usePower(..., {fastForward: true})` is not the right shortcut for the requested interaction. The new opt-in activation path must deliberately support PCs and replace the existing consuming chat action with a genuinely informational Show in Chat action. [System actor source, lines 2202–2256](https://github.com/EndlesNights/dnd4eBeta/blob/0.9.3/module/documents/actor.mjs#L2202-L2256).

`Item4e.rollAttack(options)` resolves the weapon, checks required equipment and `hasAttack`, constructs the normal attack roll configuration, and calls `d20Roll`. Calling it normally retains the system's attack bonuses, dialog, resource handling, chat output, and attack hooks. Do not reproduce its arithmetic in the HUD or target selector. [Item attack flow, lines 1602–1771](https://github.com/EndlesNights/dnd4eBeta/blob/0.9.3/module/documents/item.mjs#L1602-L1771).

## Define the first version precisely

Recommended eligibility: an owned power with an attack, a concrete source token on the current square-grid scene, and `system.rangeType` equal to `weapon`, `melee`, or `range`. **The stored key for “Ranged X” is `range`, not `ranged`.** Exclude touch, reach, personal, bursts, blasts, walls, and auras initially. Having the Weapon keyword alone does not qualify a burst or blast: classify by range type. [Range configuration, lines 1496–1568](https://github.com/EndlesNights/dnd4eBeta/blob/0.9.3/module/config.mjs#L1496-L1568).

Additionally require the power's Enable Target Automation flag and a configured positive integer Amount of Targets. Count distinct token IDs, not actors: two linked tokens remain two targets. An exact count supports multiple distinct targets immediately, but does not model repeated attacks against one target or staged secondary attacks. The system stores `target`, `trigger`, `requirement`, and `special` as strings; do not infer enemy-only, count, or sequence from these strings. [Power schema, lines 25–60](https://github.com/EndlesNights/dnd4eBeta/blob/0.9.3/module/data/item/power.mjs#L25-L60).

Revised required interaction:

1. Press **Use Ability**. Resolve and retain the power, actor, exact source token, scene, effective range, and weapon. Post one session-owned provisional card to chat without reducing uses or triggering effects/macros. Show the square and a small independent targeting panel. Start with a fresh session selection; retain previous targets only for possible restoration.
2. The panel shows the selected power using the existing chat-card visual treatment, with action buttons and mechanical effect controls omitted. Preserve authored rules prose, including an Effect paragraph needed to understand the power. Show every selected target with its name, image, validity/reason, removal control, and a selected/required counter. Never reveal hidden tokens; a no-longer-visible target becomes a generic unavailable entry.
3. Left-click a token to toggle it without changing the controlled attacker. Selection does not advance the flow. An invalid selection produces an immediate warning and remains visibly invalid until removed or made valid. Over-selection also remains visible and invalid; do not silently drop extra tokens or count only the valid subset. Observe standard target changes as well so keyboard targeting cannot bypass the panel.
4. The bottom **Attack** button glows prominently only when the selection contains exactly the configured number of distinct targets and every target passes known checks. Include readable ready/not-ready text. Keep Attack actionable even with invalid selections, including too few or too many targets. Pressing it revalidates and shows a warning dialog listing the problems, with **Return to Targeting** and **Proceed Anyway** actions. Proceed Anyway opens the normal attack dialog with the selected targets; selection warnings do not block attacking. Dismissing the warning returns to targeting without consuming anything.
5. With a valid exact selection, or after explicit Proceed Anyway confirmation, Attack locks the confirmed context, removes or suspends the selector, and opens the ordinary attack dialog once. Revalidate immediately before handoff and protect that target set through submission. Canceling the native dialog returns to selection without starting a second chat card or spending a use; explicitly exiting selection removes the provisional card.
6. On a committed attack, retain the card as the played power and commit the power's use exactly once. The targeting panel must have a visible **Cancel** button beside Attack. Pressing Cancel exits the flow without consuming a use. Cancel/close, Escape, source deletion, scene change, loss of permission, or replacing this session cancels targeting and removes its provisional message and temporary handlers/graphics. Interpret “auto-delete the ability” as deleting that chat message, **never** deleting the actor's embedded power. Do not bind ordinary right-click cancellation if it is needed for canvas pan; use explicit Cancel/Escape as the reliable paths.

The dialog-cancellation return and commit point above are recommended lifecycle choices. A separate **Show in Chat** action posts a permanent informational card, starts no session, and consumes nothing; exiting another session never deletes that card. Both informational/provisional cards should omit attack/effect controls that could bypass validation. After an attack is committed, normal follow-up damage/effect actions may be restored through the committed-card mode. Any Attack/re-attack control must route back through activation or remain absent; it must not become a native-roll bypass.

## Per-power Automation tab

Add a power-only **Automation** tab with exactly the requested initial controls: **Enable Target Automation** (default false) and **Amount of Targets** (positive integer, suggested initial value 1). Store these as namespaced module flags, conceptually `flags.<activation-module-id>.targetAutomation.enabled` and `.targetCount`, rather than adding unsupported system-schema fields. An enabled power with missing/invalid count must show a configuration warning and block its automated activation; do not silently bypass enabled enforcement. Disabling automation, or the feature's global/client setting, retains ordinary use behavior.

The pinned item sheet is already an ApplicationV2 `ItemSheetV2` with static `PARTS` and `TABS`; its form submits on change. The tab integration must participate in its actual tab/part context and await permission-checked item flag updates. Merely appending HTML after render does not establish working tab navigation or flag persistence. A scoped sheet extension/adapter is feasible, but compatibility with replacement item sheets must be tested. [Item sheet, lines 12–39 and 79–167](https://github.com/EndlesNights/dnd4eBeta/blob/0.9.3/module/applications/sheets/item-sheet.mjs#L12-L167).

**Validity contract:** these two fields specify whether automation applies and how many distinct tokens are required. Known range and configured count can be checked and warned about, with an explicit Proceed Anyway override. Missing/deleted documents and the user's authority to use the source power remain technical/permission prerequisites; the override cannot reveal hidden tokens or bypass Foundry permissions. Neither field expresses allies versus enemies, living versus undead, self exclusion, or line-of-effect exceptions. Do not label those unconfigured restrictions as checked. More complete eligibility checks need future structured controls; the original Target text remains visible for player judgment.

**Validation boundary:** the initial service presents these checks and explicit overrides for Use Ability and other callers explicitly routed through it. Native sheets, macros, and historical chat Attack buttons can still call the system directly. Applying this warning flow to every attack globally requires a separately scoped central integration with compatibility work; the HUD-independent service alone does not establish that guarantee.

## Reusing cards without activating the power

The system already has `Item4e.toChat()`, explicitly designed to post a card without macros, effect transfer, or consumption, using the same native card template with `isRoll: false`. This is the correct reference for informational presentation. However, it calls `ChatMessage.create` without awaiting or returning the message, so it does not directly give a reliable message ID for provisional-session cleanup. [Informational card path, lines 1204–1292](https://github.com/EndlesNights/dnd4eBeta/blob/0.9.3/module/documents/item.mjs#L1204-L1292).

Extract/reuse a side-effect-free card-data/rendering adapter based on that path, then explicitly await message creation and retain its ID. Reuse [PowerChatCards](../../src/banter-4e-modifications/scripts/modules/chat-rolls/power-chat-cards.js) for the established visual style through a shared presentation interface. Its current formatter deliberately preserves native actions/effects, so add explicit read-only presentation modes instead of cloning live chat DOM or attaching its action handlers to the panel. Distinguish panel, informational/provisional chat, and committed chat modes. Keep this presentation seam independent of either HUD or activation lifecycle.

Do **not** use `item.roll({createMessage: false})` as a pure renderer. Pre/sub macros, card-resource consumption, and automatic effect application occur before the create-message branch; bypassing `actor.usePower` only avoids its limited-use decrement, not these other side effects. [Item roll, lines 1058–1201](https://github.com/EndlesNights/dnd4eBeta/blob/0.9.3/module/documents/item.mjs#L1058-L1201).

Provisional messages need a namespaced session ID, author/source identity, and provisional state. Delete only the retained message belonging to that session. Respect message visibility settings and deletion authority. A closed browser or lost connection cannot guarantee immediate cleanup: reconcile abandoned provisional messages on reconnect, with permission-aware failure reporting or GM assistance where needed. Never delete by “latest message” or by all cards for an item. [Foundry v14 ChatMessage permission/deletion API](https://foundryvtt.com/api/v14/classes/foundry.documents.ChatMessage.html#canUserModify).

## Range resolution and geometry

For Melee X and Ranged X, use the structured `rangePower` formula evaluated with the actor's roll data. It is a deterministic formula field, not necessarily an integer literal. Invalid, missing, nonfinite, negative, or unsupported results must block enabled automation with a clear explanation rather than inventing a range or silently bypassing validation. Do not parse localized tooltips or `rangeText`. [Power schema](https://github.com/EndlesNights/dnd4eBeta/blob/0.9.3/module/data/item/power.mjs#L32-L43), [system range labeling/formula evaluation, lines 921–978](https://github.com/EndlesNights/dnd4eBeta/blob/0.9.3/module/documents/item.mjs#L921-L978).

For Weapon range, resolve the same equipped weapon as the attack flow. `getWeaponUse` handles an explicit weapon ID, default main hand, default off hand, melee/ranged/implement/any categories, and thrown weapons. An independent simplified “first equipped weapon” lookup will disagree with the roll. Use the system resolver through a verified exported access path, or isolate a version-specific adapter if it is not publicly exposed. [Weapon resolver, lines 77–145](https://github.com/EndlesNights/dnd4eBeta/blob/0.9.3/module/utils/utils.mjs#L77-L145).

The system's display logic treats ordinary melee weapon reach as 1 or 2 using `properties.rch`; ranged weapons store normal and long ranges separately. Thrown melee weapons need explicit handling: the weapon's category, `isRanged`, properties, and the power's selected use mode cannot safely be collapsed into one boolean. Also, the weapon range label at item source line 928 repeats the normal value for both values; this is another reason not to read display labels. [Weapon schema, lines 32–50](https://github.com/EndlesNights/dnd4eBeta/blob/0.9.3/module/data/item/weapon.mjs#L32-L50), [range labels](https://github.com/EndlesNights/dnd4eBeta/blob/0.9.3/module/documents/item.mjs#L921-L943).

Decide long-range policy explicitly. Recommended: draw the normal range boundary and, where applicable, a second labeled long-range boundary, allowing targets inside maximum range while preserving the system's long-range penalty. A normal-range-only MVP is simpler but deliberately excludes legal long-range attacks. DnD4e already infers the long-range attack bonus from distance and the selected weapon/power. [Dice helper, lines 89–113](https://github.com/EndlesNights/dnd4eBeta/blob/0.9.3/module/helpers/dice.mjs#L89-L113).

A square is appropriate for equal-cost diagonals on a square grid. For a 1×1 source and range N, the outer footprint spans 2N+1 squares; for a larger source, expand its occupied footprint by N on each side. Test target occupied squares, not only the target's center or the click point. Foundry supports configurable square-grid diagonals, so choose and document whether this feature enforces the campaign's 4e square counting or follows scene settings. Overlay and acceptance must use the same policy. [Foundry v14 SquareGrid API](https://foundryvtt.com/api/v14/classes/foundry.grid.SquareGrid.html).

The system's own distance helper samples occupied token spaces and takes the minimum measured distance, with an optional wall check. It is not simply center-to-center distance. Verify agreement for large, fractional, offset, and differently sized tokens, and scene distance units before enforcing hard boundaries. Initially exclude gridless/hex scenes and ambiguous elevation cases; explain that automation is unsupported instead of silently allowing an unvalidated attack. [Distance helper, lines 1517–1582](https://github.com/EndlesNights/dnd4eBeta/blob/0.9.3/module/utils/utils.mjs#L1517-L1582).

## Limitations that matter most

### Opening a dialog is affected by fast-forward preferences

Calling `rollAttack()` does not guarantee a dialog for every user. The dice helper consults the system's fast-forward preference and modifier key; its `options.fastForward` override only applies when truthy, so passing `{fastForward: false}` through this attack API does not reliably force a dialog. The adapter must explicitly resolve this behavior if the requirement is to always open a dialog, without temporarily changing a shared/user setting. A narrowly scoped compatibility adjustment may be needed. [Fast-forward merge, lines 829–844](https://github.com/EndlesNights/dnd4eBeta/blob/0.9.3/module/helpers/dice.mjs#L829-L844), [preference evaluation, lines 1167–1169](https://github.com/EndlesNights/dnd4eBeta/blob/0.9.3/module/utils/utils.mjs#L1167-L1169).

### Targets are mutable global user state

The system reads `game.user.targets` when preparing dialog targets and bonuses, reads its size again during submission, and reads the token list again when constructing the roll. The panel's confirmed set is therefore not a sealed target argument passed through the entire attack. Merely targeting the validated tokens and immediately restoring the old selection can produce the wrong attack. [Dice helper, lines 66–67, 263, and 440](https://github.com/EndlesNights/dnd4eBeta/blob/0.9.3/module/helpers/dice.mjs#L66-L67).

Hold the activation session through dialog completion. Prevent target changes while the native dialog owns the selection, or cancel its submission and return to selection with a warning. Recheck token movement, item/range edits, count, and permissions at final submission as well. Keep any Proceed Anyway acknowledgement scoped to the exact confirmed selection and reported issues: new selection problems should offer the same warning/override choice, rather than silently blocking or silently inheriting an old acknowledgement. Permission failures and missing source documents remain technical failures. This requires an audited submission/target-context adapter; the post-roll hook is too late to present a pre-attack warning. Passing an undocumented `targets` option is not an established solution. Restore previous targets only on full session cancellation and only where this does not overwrite later intentional changes. Leave successful targets selected for subsequent damage/effects unless a later design changes that policy.

### Ordinary left-click normally has other jobs

Foundry provides public `Token.setTarget(true, {releaseOthers: true})`, but its `targetToken` hook reports a target change; it is not a cancellable generic token left-click interception hook. The documented token click internals are protected, and the hook catalog does not establish a public `clickLeftToken` hook. [Token API](https://foundryvtt.com/api/v14/classes/foundry.canvas.placeables.Token.html#setTarget), [targetToken hook](https://foundryvtt.com/api/v14/functions/hookEvents.targetToken.html).

Use a temporary modal canvas interaction surface or a narrowly scoped, audited v14 interaction adapter. It must consume only clicks belonging to an active targeting session and preserve pan, zoom, drag, and ordinary selection outside it. Target clicking must not switch the controlled token and thereby move the HUD to a different actor, especially for the GM. Other canvas modules may compete for the same events. This is the main interaction risk requiring user testing, rather than a reason the entire feature is impossible.

### Actor identity is not enough to identify the attacker

The system's `tokenForActor` returns the first token from its candidate lookup and is used for automatic attack bonuses. If several linked tokens share an actor, an overlay around one token does not guarantee the system calculates distance/flanking from that same token. Pass the exact source token into the independent service and initially require an unambiguous controlled source; resolving the remaining system token ambiguity may require adapter work. [Token helper, lines 1375–1380](https://github.com/EndlesNights/dnd4eBeta/blob/0.9.3/module/utils/utils.mjs#L1375-L1380), [attack bonus caller](https://github.com/EndlesNights/dnd4eBeta/blob/0.9.3/module/helpers/dice.mjs#L89).

### Range does not prove attack legality

A square alone says nothing about line of sight/effect, walls, cover, concealment, enemy/ally restrictions, invisibility, terrain, ammunition, requirements, secondary targets, or special exceptions. Do not reveal hidden tokens or derive player overlays from inaccessible objects. Do not equate a movement-wall collision test with all attack legality rules. Retain normal system bonuses and GM judgment; any stricter wall/visibility policy needs its own rules and tests. The existing system calculates several conditional bonuses, but this is distinct from a general legality validator. [Bonus evaluation, lines 89–150](https://github.com/EndlesNights/dnd4eBeta/blob/0.9.3/module/helpers/dice.mjs#L89-L150).

### Consumption and cancellation are not transactional

HUD NPC activation currently consumes a use before the dialog, and `actor.usePower` also consumes limited uses before posting its card. `rollAttack` separately handles attack resources after its dialog resolves. The revised service must bypass pre-consumption when starting selection and commit the limited use exactly once on a real attack, preserving the system's turn/round-use policy. Canceling either selection or an unsubmitted attack dialog must consume nothing. Keep ammunition in the normal attack pipeline, and account separately for attributes/materials/charges normally consumed on card use. [HUD controller, lines 373–402](../../src/dnd4e-health-display/scripts/actor-display/actor-display.js), [actor use flow](https://github.com/EndlesNights/dnd4eBeta/blob/0.9.3/module/documents/actor.mjs#L2208-L2234), [attack resource handling](https://github.com/EndlesNights/dnd4eBeta/blob/0.9.3/module/documents/item.mjs#L1763-L1771), [resource modes, lines 1295–1320](https://github.com/EndlesNights/dnd4eBeta/blob/0.9.3/module/documents/item.mjs#L1295-L1320).

There is no atomic transaction covering a chat roll, resource update, macros, and effects. Check availability immediately before commit, prevent double-click/double submission, and explicitly track whether a roll was emitted before treating a null/error result as safe to retry. Preserving use-time macros/self effects while postponing them from provisional-card creation also needs a documented commit stage: either support those hooks once at commitment, or identify affected powers as unsupported. Do not silently drop them or execute them while merely showing a card.

## Architecture that survives a HUD rewrite

Recommended boundaries:

- **Activation service:** owns the setting, per-power automation configuration, one active session per user, targeting panel, provisional message identity, validation, cancellation, and commit. Public entry point conceptually accepts `{item, sourceToken}` and returns completed, cancelled, unsupported, or failed. Model selecting, native-dialog-open, committing, completed, and cancelled as explicit lifecycle states.
- **DnD4e 0.9.3 adapter:** owns structured range evaluation, actual weapon resolution, token identity quirks, roll options, and use-consumption policy. Revalidate item/weapon/range and permissions immediately before opening the dialog. Item changes during selection invalidate the preview; either recompute it or cancel. Do not assume a standard dialog weapon selector exists: if another module or future UI allows weapon changes, revalidation/locking becomes necessary.
- **Canvas selector:** owns disposable local graphics and temporary input handling. It receives already resolved geometry and candidate rules, not HUD DOM references.
- **Card presentation:** builds the same read-only power view for the targeting panel and provisional/informational chat, without initiating use or binding native attack/effect controls. The service owns message creation/deletion; the renderer does not.
- **Power-sheet adapter:** exposes the Automation tab and persists validated module flags independently of HUD code.
- **HUD adapter:** forwards Use Ability and the exact source token to the service, and exposes separate Show in Chat. It retains right-click sheets and ordinary behavior when automation is disabled. It owns no selection session or geometry.

A separate `scripts/power-activation/` feature inside Info Displays is enough to survive a HUD rewrite if registered from the module entry point and independent of HUD classes/templates. A **standalone Foundry module** is stronger: it also survives replacing or uninstalling Info Displays, and other HUDs/macros can invoke the same public API. Given the stated long-term reuse goal, prefer the standalone module if “change the entire HUD” includes changing packages. Avoid a global patch to every `rollAttack` just to support this HUD; explicit callers are easier to keep scoped.

Recommended setting: an opt-in world setting, default off, named “Enable power target automation,” plus each power's enable flag. World scope fits presenting the configured workflow consistently; client scope remains an alternative if individual opt-in is preferred. With the setting or power flag disabled, preserve ordinary use behavior and the informational Show in Chat action. An enabled power with unsupported geometry or invalid configuration must explain why automation cannot proceed, rather than silently entering an unvalidated roll. A manual fallback should require explicitly disabling automation for that power or a separately designed GM action.

Preserve repository integrations: [TargetingWarning](../../src/banter-4e-modifications/scripts/modules/targeting-warning/targeting-warning.js) wraps `rollAttack` and checks selected targets; [player-defense](../../src/banter-4e-modifications/scripts/modules/player-defense/player-defense.js) consumes `dnd4e.rollAttack`; [cover-preview](../../src/banter-4e-modifications/scripts/modules/cover-preview/cover-preview.js) observes current targets and controlled attacker. Select the target before entering the normal pipeline, retain its hooks, and do not replace the controlled attacker. The system emits its attack hook with populated target results, which is another reason to keep its normal calculation path. [System hook emission, lines 583–588](https://github.com/EndlesNights/dnd4eBeta/blob/0.9.3/module/helpers/dice.mjs#L583-L588).

## Expansion path and validation

First prove the complete panel lifecycle for configured exact-count Melee X/Ranged X powers, including multiple distinct targets, provisional card cleanup, and deferred consumption. Then add deterministic Weapon range, reach/thrown variants, and normal/long-range boundaries. Add richer eligibility metadata and min/max counts before powers with optional targets or repeated/secondary attacks. Only then add bursts, blasts, walls, and auras with placement/area adapters. The system already distinguishes area powers and has template placement; reuse that workflow rather than stretching a source-centered square into every ability type. [Area recognition](https://github.com/EndlesNights/dnd4eBeta/blob/0.9.3/module/documents/item.mjs#L526), [template placement, lines 1975 onward](https://github.com/EndlesNights/dnd4eBeta/blob/0.9.3/module/documents/item.mjs#L1975).

Eventually most abilities will need normalized metadata: selection shape, origin, minimum/maximum targets, ally/enemy/self policy, repeated attacks, secondary attack stages, movement requirements, and explicit exceptions. Keep a manual fallback for narrative/custom powers. Do not claim full automation from parsing English descriptions.

Implementation should test range/formula normalization, occupied-space boundaries, weapon resolution, exact/under/over count, invalid selections, Return to Targeting and Proceed Anyway (including under/over count), visible panel Cancel cleanup, validation on both Attack and native submission, and cancellation without use loss. Verify that informational/provisional rendering invokes no use macros/resources/effects; Show in Chat survives session cancellation; only the session's provisional message is deleted; repeated clicks cannot commit twice; and Automation flags persist through sheet edits and item copies/imports. Test permission failures, reconnect cleanup, dialog cancellation returning to selection, and successful-card retention. The repository has tests under [Info Displays test](../../src/dnd4e-health-display/test/), despite the module skill's older “no automated tests” note. Actual canvas click ordering, GM/player ownership, linked/unlinked tokens, large tokens, movement during selection/dialog, hidden targets, long range, competing modules, replacement sheets, active defense, and disabled-setting behavior require user-operated Foundry reload/manual verification. No Foundry runtime was launched or inspected for this investigation.

Foundry references are explicitly v14. Runtime feasibility remains unproven until the user exercises a prototype in their installed environment.
